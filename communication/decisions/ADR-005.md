# ADR-005 — Universal Screen Identity Migration is its own project phase

**Type**: Architecture Decision Record (Director-issued, binding).
**Context**: TASK-002C freeze review.

## Decision

Migrating TASK-001's pre-ADR-002 registrations (any `NavigationNode`/
`MenuDefinition` id not following the dotted Universal Screen Identity
convention) to the new format is **not** a side effect of any other
task. It is its own, separately-scoped Migration Task, governed by:

- **No silent migration.** A migration is never folded into an
  unrelated task's diff.
- **Frozen tasks are not modified.** PLATFORM-001/TASK-002A/002B/002C's
  own already-approved content is not rewritten to retrofit the new
  convention (`platform_layer/platform_service/navigation_model.py`'s `is_valid_screen_id()`
  already documents this exact reasoning — this ADR formalizes it as
  binding policy, not just one function's docstring rationale).
- **Migration happens through a dedicated task**, with its own
  Analysis → Architecture → Implementation Plan → Approval Check
  sequence per `docs/PLATFORM_WORKFLOW.md` — not authorized by this
  ADR itself.
- **A Backward Compatibility plan is mandatory** before that task's
  Implementation step — stating what still works, unchanged, for any
  caller using the pre-migration id.
- **A Rollback plan is mandatory** — how to undo the migration if it
  turns out wrong, before it ships.

## Why

TASK-002C's own `is_valid_screen_id()` deliberately did not enforce
the new convention retroactively, to avoid silently breaking a frozen
contract. This ADR makes that same restraint a standing rule for any
future migration, not a one-off judgment call repeated ad hoc each
time the question comes up.

## Status

Approved — Director decision, effective immediately. No migration task
is currently scheduled or authorized by this ADR; it only states the
rules such a task must follow whenever the Director does schedule one.
