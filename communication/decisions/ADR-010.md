# ADR-010 — Fail Closed Permission Policy

**Type**: Architecture Decision Record (Director-issued, binding).
**Context**: TASK-002E security review — the Director's response to
the `has_sufficient_permission()` observation the Worker surfaced
without self-authorizing a fix.

**Numbering note**: the Director's review named this decision
"ADR-009," but ADR-009 is already assigned
(`communication/decisions/ADR-009.md`, the CI Supersession Rule,
approved at TASK-002D's freeze). Recorded here as **ADR-010** instead
so no existing record is overwritten — flagged explicitly per the No
Silent Decisions Policy rather than silently renumbering without
saying so. The Director's second new decision (Security Review Layer)
is recorded as ADR-011 for the same reason.

## Decision

Any permission check in this codebase — present or future, in
`platform_layer/platform_service/navigation_core.py` or any later Permission/Authentication/
Authorization/Session/Navigation module — must **fail closed**. An
unknown, invalid, missing, or malformed permission value (on either
side of the comparison: the tier held, or the tier required) never
grants access. It always evaluates to **DENY**. "Allow" is never the
default; it must be affirmatively earned by a recognized, valid value
on both sides of the check.

## Why

`has_sufficient_permission()` (`platform_layer/platform_service/navigation_core.py`,
Frozen) ranks an unrecognized tier at `-1` via
`_TIER_RANK.get(tier, -1)`. For the *user*-tier side this correctly
fails closed (`-1 >= anything real` is false). For the *required*-tier
side it does not: any real user tier (rank ≥0) satisfies `>= -1`,
so an empty or malformed `required_tier` is treated as "no restriction"
rather than "no access" — the opposite of the intended security
posture. A permission system's safe default must be the same in both
directions.

## Status

**Approved — a standing rule for all future Permission/Authentication/
Authorization/Session/Navigation work.** Not applied retroactively to
`platform_layer/platform_service/navigation_core.py` in this cycle — that module is Frozen
per TASK-002D/TASK-002E's own Freeze Checklists, and a Frozen module is
only reopened for a critical bug, a security issue, a Director-approved
ADR, or a future Migration Task. This ADR is the Director-approved ADR
that authorizes reopening it — but the Director has separately ordered
(per the TASK-002E review) that the actual code fix is deferred to a
dedicated future Security Task, tracked as a Security Backlog entry in
`docs/TECHNICAL_DEBT.md`, not applied silently inside this ADR.

## Applies to

Every future Permission/Authentication/Authorization/Session/
Navigation module, recorded as a standing rule in
`docs/PLATFORM_WORKFLOW.md`. The one known non-conforming case today
(`has_sufficient_permission()`'s required-tier direction) is tracked,
not fixed, in `docs/TECHNICAL_DEBT.md`.
