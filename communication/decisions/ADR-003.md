# ADR-003 — Platform never creates a Screen

**Type**: Architecture Decision Record (Director-issued, binding).
**Context**: TASK-002B (Navigation Architecture) review.

## Decision

A platform only ever *calls* Navigation to reach a screen — it never
constructs one itself.

**Forbidden**:
```
Telegram → Create Screen
```

**Required**:
```
Screen Registry → Navigation → Platform Adapter → Telegram
```

(or any other client in place of Telegram — Android, iOS, Desktop,
Mini App follow the identical shape).

## Why

If a platform could construct its own Screen ad hoc, that platform's
version of the screen could silently diverge from every other
platform's — defeating ADR-002's Universal Screen Identity the moment
any client takes a shortcut.

## Impact

- Every Screen a client shows must already exist in the Screen/Route
  Registry (`platform_layer/platform_service/menu_registry.py`'s successor, per
  `docs/NAVIGATION_ARCHITECTURE.md` §4) before any Platform Adapter
  (§8) can render it.
- `platform_layer/telegram/reply_keyboard_manager.py`/`platform_layer/telegram/keyboards.py` are
  **not** modified by this decision — they remain the live, unwired
  Telegram implementation until a separately-approved task adapts
  them; this ADR governs the target shape for that future adaptation,
  not today's code.

## Status

Approved — Director decision, effective immediately.
