# ADR-006 — Navigation Transaction

**Type**: Architecture Decision Record (Director-issued, binding).
**Context**: TASK-002D review. **Governs future Navigation work — see
"Applies to" below; does not retroactively rewrite already-approved
TASK-002D content.**

## Decision

Every Navigation operation runs as a transaction:

```
Start Navigation
    ↓
Permission
    ↓
Resolve Route
    ↓
Update Stack
    ↓
Emit Events
    ↓
Commit
```

If any stage fails, the whole operation rolls back. Navigation must
never leave a session in a half-updated state (e.g. the stack updated
but the corresponding event never produced, or vice versa).

## Why

A partially-applied navigation (stack changed, event lost — or an
event fired for a navigation that didn't actually happen) is a
silent-corruption risk once multiple platforms and a future Event Bus
consumer (Analytics, AI) depend on Navigation State being trustworthy.

## Applies to

Future Navigation implementation work — most immediately relevant to
whatever comes after TASK-002D. `platforms/navigation_core.py`'s
current `NavigationCore.navigate()`/`go_back()` (TASK-002D, pending
CI confirmation) already fail atomically in practice (a
`PERMISSION_DENIED`/`NAVIGATION_FAILED` result never touches the stack
at all — see that module's own tests), but do not yet name this
explicit Start→Commit/Rollback shape or handle a mid-operation failure
between multiple stages. Formalizing that shape into the code is a
separately-scoped follow-up, not silently applied to TASK-002D's
already-reviewed content (No Silent Decisions Policy).

## Status

Approved — Director decision, effective immediately as a governing
principle. Implementation against `platforms/navigation_core.py` is a
future task.
