# GoldBot v0.3.5 Implementation Specification (Phase A1, Task 4)

Specification only — **no implementation in this document or this
phase.** Every module below describes what a future, separately-
approved implementation phase should build, grounded in the concrete
gaps found in `docs/FOUNDATION_GAP_ANALYSIS.md` and the real code
surfaces found in `docs/ARCHITECTURE_AUDIT.md`. Ordered per that
document's Recommended Order.

Every item touching `decision_layer/decision_engine/decision_engine.py` or
`risk_layer/risk_engine/risk_manager.py` remains subject to `CLAUDE.md`'s Trading Safety
rule: explicit approval required before any implementation, even once
a specification exists here.

---

## 1. HTF Bias Module

**Purpose**: classify higher-timeframe (H4/H1) directional bias so
M15 execution-context signals can be evaluated against it, per the
roadmap's `H4/H1 Analysis → HTF Bias → M15 Execution Context` diagram.

**Responsibilities**:
- Consume multi-timeframe candle data (already produced by
  `MarketDataNormalizer.get_snapshot()` — see Foundation Gap Analysis
  item 1, this is the one piece that already exists).
- Classify each higher timeframe's structural direction using the
  same primitives `context_layer/market_structure/market_structure.py` already provides
  (`detect_swing_points()`, `classify_structure()` — HH/HL/LH/LL) run
  against the H4 and H1 candle series independently.
- Resolve H4 and H1 into one `HTFBias` value (e.g. `BULLISH` /
  `BEARISH` / `NEUTRAL`/`CONFLICTED` — exact enum values are an
  implementation decision, not specified here) — a rule for how
  disagreement between H4 and H1 should resolve needs its own explicit
  decision at implementation time (this specification intentionally
  does not choose one).

**Inputs**: `Dict[str, List[Candle]]` keyed by interval (`"H4"`,
`"H1"`) — the shape `MarketSnapshot.candles` already provides.

**Outputs**: a new, immutable `HTFBias` value (dataclass or enum,
implementation's choice) — proposed as a new field on
`ContextSnapshot` (`context_layer/context_engine/context_orchestrator.py`), since
`ContextSnapshot`'s own docstring already states it is "consumed by
the Strategy Layer, AI Layer, and any downstream engine" — the same
contract an HTF bias result should join.

**Dependencies**: `context_layer/market_structure/market_structure.py` (reused, not
duplicated — `CLAUDE.md`'s "No duplicate logic" rule applies), and
`data_layer/live_data/market_data.py`'s existing `get_snapshot()` — no new external
dependency needed.

**Future extensions**: once `HTFBias` exists on `ContextSnapshot`, it
becomes a natural input to both a future Wyckoff phase classifier
(phase context often differs by timeframe) and the Decision Engine
rework below.

**Not specified here (implementation decisions, deliberately left
open)**: the exact bias-resolution rule when H4 and H1 disagree; the
exact enum values; whether M5 also participates or only H4+H1; whether
a "distance from HTF swing" numeric score accompanies the categorical
bias.

## 2. Decision Engine v2 — Signal Quality Score

**Purpose**: replace `DecisionEngine.evaluate()`'s current flat,
unweighted two-input average with a scoring model that has room for
the inputs this audit found were named in the roadmap but don't exist
in the current formula: a distinct Technical Score, an HTF-bias
input, and an actual Risk Score (as opposed to the currently-dead
`DecisionResult.risk_score` field).

**Responsibilities**: produce the same `TradeDecision` contract
(`action`, `confidence`, `reason`, `signal`, `ai_analysis`) the
pipeline and every downstream consumer (`risk_layer/risk_engine/risk_manager.py`,
`platform_layer/telegram/signal_formatter.py`, `database_layer/trade_repository/signal_record.py`) already
depend on — this specification proposes **no breaking change to
`TradeDecision`'s shape**, only to how `confidence` is computed
internally.

**Inputs** (proposed, three components instead of today's two):
1. **Technical Score** — `SignalCandidate.confidence`, as today, but
   the specification recommends this stop being one opaque number and
   instead carry (or be accompanied by) which strategy produced it, so
   a future per-strategy weighting is possible without another
   `SignalCandidate` schema change later.
2. **AI Score** — `AIAnalysisResult.confidence`, unchanged.
3. **HTF Bias alignment** — whether the signal's direction agrees with
   `ContextSnapshot.htf_bias` (from Module 1 above) — proposed as a
   multiplier/bonus rather than a third averaged term, so a strong
   technical+AI setup against HTF bias is dampened rather than
   necessarily rejected outright (exact mechanism is an implementation
   decision).

**Outputs**: `TradeDecision`, unchanged shape. `DecisionConfig` gains
new tunables (exact names/defaults are an implementation decision);
existing `min_confidence`/`approve_confidence` semantics should be
preserved or explicitly migrated, not silently redefined.

**Dependencies**: `signals/` (unchanged), `ai/` (unchanged), and the
new HTF Bias output from Module 1 — this is why HTF Bias is
sequenced before this item in the Recommended Order.

**Future extensions**: this is also the natural place a future
Wyckoff-phase input or a Session-Intelligence input would plug in,
once those exist — the specification recommends designing the v2
formula as an explicitly extensible weighted-input list from the
start, rather than a fixed 2- or 3-term average, specifically so
Wyckoff/Session don't require a third rewrite of this function later.

**Explicit non-goal**: this specification does not resurrect or
repurpose the dead `DecisionResult`/`risk_score` dataclass found in
the Architecture Audit — that class has zero callers today and
`docs/ARCHITECTURE_AUDIT.md`'s recommendation is to remove it (in a
separately-approved cleanup), not build on top of it.

**CLAUDE.md note**: `decision_layer/decision_engine/decision_engine.py`'s thresholds are
named explicitly as requiring approval to change — this specification
existing does not constitute that approval.

## 3. Wyckoff Engine

**Purpose**: a multi-market-framework-agnostic phase classifier
(Accumulation / Markup / Distribution / Markdown, with Spring/UTAD
event detection), as named directly in the Phase A1 brief and
confirmed entirely absent by this audit.

**Responsibilities**: detect Wyckoff phase boundaries and the Spring/
UTAD test-of-support/resistance events within a phase, producing
structured events analogous in shape to `context_layer/market_structure/bos.py`'s
`BosEvent`/`context_layer/market_structure/choch.py`'s `ChochEvent` (a `WyckoffEvent`
dataclass with a phase/event-type enum, an index, and a timestamp) —
this specification recommends following that existing pattern rather
than inventing a new shape.

**Inputs**: `Sequence[Candle]` (same as every other `context/`
detector) — plus, if phase/Spring/UTAD detection requires volume
confirmation (conventional in Wyckoff analysis), **a new data source
this codebase does not currently have**: `data_layer/providers/twelve_data_client.py`'s
candle payload is OHLC-only today (confirmed this phase). Whether
volume is fetched from Twelve Data (if available on the current plan/
endpoint) or the initial Wyckoff implementation proceeds
price-action-only (no volume) is an open implementation decision this
specification deliberately does not resolve — it is significant enough
to warrant its own scoping conversation before implementation starts.

**Outputs**: `Sequence[WyckoffEvent]` — proposed as a new
`ContextSnapshot` field, following the same pattern as
`amd_events`/`bos_events`/`choch_events`.

**Dependencies**: `context_layer/market_structure/market_structure.py` (swing points are a
natural input to phase-boundary detection, same reuse principle as
Module 1), and — if volume is in scope — a `data/` layer change to
fetch and normalize it (out of this specification's scope to detail
further without that decision being made first).

**Future extensions**: `strategy_layer/strategy_library/wyckoff_strategy.py` (new file,
following the existing `LiquidityStrategy`/`FVGStrategy`/
`AMDStrategy` pattern exactly, registered in
`StrategyManager.__init__`'s strategy list) is the natural next step
once the context-layer detector exists — this specification treats
the strategy file as a follow-on, not part of this same
implementation unit, since `strategies/`'s current lack of a shared
interface/ABC (noted in the Architecture Audit) is worth resolving
first so a fourth strategy doesn't just extend the existing hardcoded-
list pattern.

## 4. Data Quality Surfacing

**Purpose**: connect the already-built (but unwired)
`MarketDataNormalizer.get_snapshot()`'s `quality` dict and
`_verify_timeframe_alignment()` warning to somewhere downstream can
actually observe it — currently a pure sunk cost (built, tested-
adjacent, zero consumers).

**Responsibilities**: no new detection logic needed — `get_snapshot()`
already computes `"OK"`/`"WARNING_GAP"`/`"ERROR_NO_DATA"` per
timeframe. The specification is purely about **wiring**:
1. `core/pipeline.py` switching its market-data call from
   `get_candles()` to `get_snapshot()` (this is also a prerequisite
   for Module 1, HTF Bias — the two share this exact wiring change,
   which is why they're sequenced adjacently in the Recommended
   Order).
2. A decision on where the resulting `quality` dict should be
   surfaced: logged only (lowest effort, matches the existing
   `_detect_missing_candles()`/`_verify_timeframe_alignment()`
   logging-only behavior), persisted alongside the signal record (a
   `database_layer/trade_repository/signal_record.py` field addition — a schema change,
   explicitly out of scope for this documentation-only phase and
   flagged here only as a future option), or exposed via a new
   Telegram admin command (a `telegram/` feature addition, also out of
   this phase's scope).

**Inputs**: `MarketSnapshot.quality` (already produced).

**Outputs**: implementation's choice per the options above — this
specification does not pick one, since the right answer depends on
whether v0.3.5 wants data-quality visibility for developers only
(logging) or for the bot's operators too (persistence/Telegram).

**Dependencies**: none beyond what already exists in `data/`.

**Future extensions**: once wired, this becomes the natural signal for
a future "skip this cycle, data quality too poor" gate — not
specified further here.

## 5. Session Intelligence

**Purpose**: extend the already-built, already-tested, but unwired
`data_layer/live_data/session_filter.py`'s `is_trading_time()` gate into the pipeline
itself, then (separately, longer-term) toward session classification.

**Responsibilities (near-term)**: wire `is_trading_time()` into
`core/pipeline.py`'s `run()` so the pipeline's own trading-hours
restriction doesn't depend entirely on
`.github/workflows/trading_bot.yml`'s external cron schedule — this
makes the restriction correct for any future execution path (e.g. the
`deploy/systemd/goldbot-pipeline.timer` alternative scheduler added in
Phase 58, which currently runs every 5 minutes with no session
awareness of its own).

**Responsibilities (longer-term, separate unit)**: classify which
session (London/New York/Asia, or GoldBot's own session boundaries) a
given candle/cycle falls into — this is a new capability, not an
extension of the existing boolean gate, and this specification treats
it as a distinct, later increment.

**Inputs**: none beyond what `is_trading_time()` already reads
(system clock).

**Outputs (near-term)**: a boolean gate at the top of
`core/pipeline.py`'s `run()` — implementation detail (early return vs.
a logged skip) left open.

**Outputs (longer-term)**: a `Session` enum value, proposed as a
`ContextSnapshot` field following the same pattern as Modules 1 and 3.

**Dependencies**: `data_layer/live_data/session_filter.py` (reused, not duplicated).

**Future extensions**: session-aware Signal Quality Score weighting
(Module 2) once session classification exists.

## 6. Trading Style Personalization

**Purpose**: connect the already-stored, already-UI-exposed
`UserRecord.trading_style` field to something that actually affects
what a user sees or how a signal is scored for them — today it is
pure display data.

**Responsibilities**: this specification deliberately stays shallow
here because the underlying architectural question — does GoldBot
move from "one global decision broadcast to `TELEGRAM_CHAT_ID`" toward
"per-user personalized signal delivery" — is a significant product
decision, not a narrow engineering spec, and is flagged as needing its
own scoping conversation before a v0.3.5-sized specification can be
written responsibly.

**Inputs / Outputs / Dependencies**: not specified further pending
that product decision.

**Future extensions**: n/a until scoped.

## 7. Asset Manager

**Purpose**: orchestrate more than one symbol, building on the fact
(confirmed in Foundation Gap Analysis) that `TradingPipeline` is
already constructor-parameterized by `symbol`/`interval` — only
`main.py`'s single hardcoded call site and the single-symbol
GitHub Actions schedule are single-asset today.

**Responsibilities**: iterate a config-driven symbol list, invoking
`TradingPipeline` once per symbol per cycle — the simplest version of
this requires no change to `TradingPipeline` itself, only to
`main.py` and a new config surface (e.g. `Config.SYMBOLS: List[str]`,
following the existing `Config.TIMEFRAME_HISTORY` pattern).

**Inputs**: a symbol list (source — `config.py`, environment variable,
or database-driven — is an implementation decision).

**Outputs**: N sequential `TradingPipeline.run()` invocations per
scheduled cycle, each independent (matches today's single-symbol
behavior's isolation properties — one symbol's failure shouldn't
affect another's, same as `core/pipeline.py`'s existing per-stage
exception handling within one run).

**Dependencies**: none beyond `core/pipeline.py` (unchanged) and
`config.py` (extended).

**Future extensions**: concurrent (rather than sequential) execution,
if GitHub Actions' or a VPS's per-run time budget becomes a constraint
with more symbols — not needed at today's single-symbol timing
(`docs/PERFORMANCE.md`'s benchmarks show sub-second pipeline compute
per cycle) and therefore not specified further here.

**Explicit non-goal**: this specification does not address per-symbol
strategy/AI/risk tuning (e.g. Forex-specific risk parameters) — that
would follow the Wyckoff engine's multi-market-agnostic framing more
than a symbol-list loop, and is out of scope here.

## 8. Monitoring Improvements

**Purpose**: resolve the two `monitoring/` findings from the
Architecture Audit — `performance.py`'s dormant `database/` dependency
(paid for, never invoked) and the package's undocumented, inconsistent
isolation posture between its two files.

**Responsibilities**: either (a) wire `core_layer/health_monitor/performance.py` into
a real caller (a Telegram admin command, following the existing
`telegram/*_service.py` → `database/*_repository.py` pattern, would be
the natural integration point since `performance.py` already imports
`SignalRepository`), or (b) explicitly document why it stays
dormant — this specification does not choose between the two, since
that depends on whether operator-facing performance reporting is a
v0.3.5 priority or a later one.

**Inputs / Outputs**: unchanged — `performance.py`'s existing
interface is not proposed to change, only its wiring status.

**Dependencies**: `database_layer.trade_repository.signal_repository.SignalRepository`
(already imported).

**Future extensions**: once genuinely wired, this becomes the natural
home for surfacing Module 4's data-quality metrics and Module 2's
Signal Quality Score history in aggregate, if a future admin-facing
analytics view is wanted.

## Explicitly Out of Scope for v0.3.5 Specification

Per the Phase A1 brief's boundaries, restated here for clarity:
- No strategy implementation, no trading-logic change, no pipeline
  behavior change, no Decision/Risk Engine code change, no AI logic
  change, no database schema change happens in this phase or as a
  direct result of this document existing.
- Every module above requires its own, separately-approved
  implementation phase — this document is the map, not the work.
