# GoldBot v0.2 — Release Notes

**Telegram Product Layer**

v0.2 turns GoldBot from a one-way "signal broadcaster" bot into a
subscription-aware, permission-gated trading-signal product with a
real user lifecycle, admin tooling, and a feedback loop — built
entirely as a Telegram-layer addition on top of the untouched v0.1
trading pipeline (Data → Context → Strategy → Signal → AI → Decision →
Risk → Telegram Delivery → Persistence).

## Features

- **User management** — `/start` registration, profile storage, and a
  lifecycle state machine (`NEW` → `ACTIVE` → `BANNED`), independent
  of subscription plan.
- **Settings** — `/settings`, `/language`, `/risk`, `/timeframe`,
  `/strategy`, `/notifications`; each validates input and persists to
  the user's profile.
- **Subscription foundation** — `/plan`, `/subscription`, `/upgrade`.
  Plans are `FREE` / `PREMIUM` / `VIP`, tracked in their own table,
  deliberately kept separate from user lifecycle state. No payment
  gateway — upgrade is a recorded request, not a transaction.
- **Signal access control** — `/signal` is gated by plan (`FREE`
  denied with an upgrade prompt; `PREMIUM`/`VIP` allowed); `/history`
  stays open to everyone as a product-discovery funnel. OWNER/ADMIN
  always bypass the plan check.
- **Admin panel** — `/admin` (role-specific view for OWNER vs ADMIN),
  `/stats`, `/users`, `/userinfo`, `/system`, `/broadcast`,
  `/addadmin`/`/removeadmin` (OWNER only).
- **Feedback system** — `/feedback` (user submission), `/feedbacks`
  (admin review, `OPEN`/`REVIEWED`/`RESOLVED` lifecycle).

## Architecture

```
Telegram User
      |
      v
Command Router  (permission gate: OWNER > ADMIN > USER)
      |
      v
Handlers  (platform_layer/telegram/handlers.py)
      |
      v
Services  (UserService, SubscriptionService, SignalAccessService,
           NotificationService, FeedbackService, AdminService)
      |
      v
Repositories  (UserRepository, SubscriptionRepository,
               SignalRepository, AdminRepository, FeedbackRepository)
      |
      v
SQLite (users, subscriptions, signals, admins, feedback)
```

The v0.1 trading pipeline (`core/pipeline.py` and everything it wires:
`signals/`, `strategies/`, `ai/`, `decision/`, `risk/`) is untouched by
v0.2 — the Telegram product layer reads from the same `signals` table
the pipeline already wrote to, and remains the sole owner of signal
*generation*. See `docs/telegram_layer.md` for the full command/service
map and `docs/database_schema.md` for the table-by-table schema.

## Known limitations (intentional, by design)

- No payment gateway (Click/Payme/Stripe) — `/upgrade` is a recorded
  request only.
- No real-time enforcement of `BANNED` status yet — the state is
  tracked and available (`UserService.ban_user()`/`activate_user()`),
  but no command currently checks it before executing.
- The scheduled pipeline's own Telegram notification (`main.py` →
  `TradingPipeline.run()` → `Notifier.send_messages()`) still delivers
  to a single fixed `TELEGRAM_CHAT_ID` (channel/group), not per-user —
  it is architecturally separate from the per-user notification
  preference (`/notifications`) and admin `/broadcast`, both of which
  are fully per-user. See `platform_layer/telegram/notification_service.py`'s module
  docstring (Phase 43) for the full reasoning.
- Inline keyboards (`platform_layer/telegram/keyboards.py`) render as hints only; all
  real interactions happen via command arguments (e.g. `/risk 5`), not
  `callback_query` taps — no callback handler is wired in
  `platform_layer/telegram/polling.py`.

## Phase 47 audit fix

`AdminService.broadcast()` was a synchronous method that internally
called `asyncio.run()`. Since `broadcast_handler()` (its only caller)
is itself async and runs inside `platform_layer/telegram/polling.py`'s already-active
event loop, every real `/broadcast` call in production would have
raised `RuntimeError: asyncio.run() cannot be called from a running
event loop` — the same nested-event-loop trap `Notifier` hit and fixed
in Phase 33.1. `broadcast()` is now `async` and is `await`-ed directly
by its caller. Covered by `tests/test_admin.py::
test_broadcast_is_async_and_safe_inside_a_running_event_loop`.

## v0.2 is now feature-frozen

No new commands, no new Telegram features, no subscription/payment
integration, and no signal-engine/AI/strategy changes should land on
top of v0.2. Further work continues under **v0.3 — Foundation
Hardening**.
