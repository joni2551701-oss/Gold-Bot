# GoldBot v0.3 — Foundation Hardening & Optimization

Release candidate notes for v0.3.0-rc1. This release contains **no
new trading features** — it is a hardening, optimization, and
professionalization pass over the v0.2 Telegram Product Layer
feature-frozen codebase, closing out the gaps a full-system audit
found and building the governance/testing/documentation foundation
v0.4 (AI Assistant Core) will be built on top of.

## Added

- ✅ **Full audit** (Phase 48) — every layer (data, context,
  strategies, signals, ai, decision, risk, execution, monitoring,
  database, telegram, security, dependencies, code quality) audited
  end to end. See `docs/AUDIT_REPORT.md`.
- ✅ **Architecture cleanup** (Phase 49) — dead code removed (6 unused
  methods/functions across `database/`/`telegram/`), `context_layer/order_block/order_block.py`
  now reuses the shared candle-sentiment helper instead of duplicating
  it, exception-safety and candle-order validation added to
  `context_layer/amd/amd.py`/`context_orchestrator.py`. `docs/code_structure.md`
  and `docs/ARCHITECTURE.md` document the resulting module map.
- ✅ **Database optimization** (Phase 50) — 6 evidence-based indexes
  added (`users`/`signals`/`feedback` on `status`/`created_at`),
  `SELECT *` narrowed to named columns where verified 100%
  behavior-identical, `database/migrations/README.md` foundation for
  future versioned migrations. See `docs/DATABASE.md`.
- ✅ **Logging system** (Phase 51) — one consistent logging standard
  across all 33+ loggers; `telegram/handlers.py`'s 68 previously-silent
  exception handlers now log; startup/shutdown lifecycle logging in
  `main.py`. See `docs/LOGGING.md`.
- ✅ **Testing framework** (Phase 52) — `tests/unit/`,
  `tests/integration/`, `tests/security/` established;
  `core/pipeline.py` and `decision_layer/decision_engine/decision_engine.py` went from 0%
  to 100% coverage; permanent regression protection added for the
  critical notification-safety fix. See `docs/TESTING.md`.
- ✅ **Performance optimization** (Phase 53) — per-stage pipeline
  timing instrumentation (`pipeline_started`/`stage=.../
  pipeline_finished`) and slow-operation detection (>2s WARNING)
  added; the dominant real bottleneck (aiogram's ~2.5s import cost)
  identified and explained. See `docs/PERFORMANCE.md`.
- ✅ **Security audit** (Phase 54) — secret management, Telegram
  permission matrix, SQL-injection resistance, input-validation
  crash-safety, file security, and dependency vulnerabilities all
  audited and dynamically proven via `tests/security/` (43 tests).
  Zero P0/P1/P2 findings. See `docs/SECURITY.md`.
- ✅ **AI foundation** (Phase 55) — `ai/interfaces.py`
  (`AIAnalyzerInterface`/`MarketContext`/`UserContext`/`AIResponse`),
  `ai/memory/`, `ai/prompts/`, `ai/profiles/` professional subpackage
  structure prepared for v0.4, with zero change to the current
  production AI stub. See `docs/AI_ARCHITECTURE.md`.
- ✅ **Documentation standard** (Phase 56) — `CLAUDE.md` engineering
  rules, `docs/ARCHITECTURE.md` + `docs/DEVELOPMENT_RULES.md`, a
  README on every major module (`data/`, `context/`, `signals/`,
  `decision/`, `risk/`, `execution/`, `database/`, `telegram/`, `ai/`),
  `docs/DEPLOYMENT.md`, `.env.example`, `requirements-freeze.txt`, and
  this release-notes document.

## Fixed

- **Critical**: rejected, risk-blocked, and geometrically-invalid
  (SL/TP on the wrong side of entry) signals were reaching Telegram
  users, and a single pipeline cycle could send more than one
  notification. Fixed in `core/pipeline.py` (candidate filtering to
  APPROVE + risk-approved only, single highest-confidence winner per
  cycle) and `risk_layer/risk_engine/risk_manager.py` (`validate_geometry()`). This was
  the triggering incident for the entire v0.3 hardening effort — full
  root-cause writeup in `docs/AUDIT_REPORT.md`.
- Two test files (`tests/test_signal_layer.py`,
  `tests/test_generate_signals.py`) silently collected **zero** tests
  despite matching pytest's discovery pattern (defined `run_test()`
  instead of `test_*` functions) — rewritten as real pytest tests
  (Phase 52).
- `AdminService.broadcast()`'s nested-event-loop crash
  (`asyncio.run()` called from an already-running loop) — fixed to a
  clean `async`/`await` chain (Phase 47).
- Six small dead/duplicate methods removed from `database/` and
  `telegram/` (Phase 49) — zero behavior change, confirmed by callers
  grep before removal.

## Known Limitations

- **AI analyzer does not make real decisions yet.**
  `ai/ai_analyzer.py`'s `AIAnalyzer.analyze()` is a permanent-reject
  heuristic stub — every signal candidate is currently rejected by
  the AI layer. This is intentional and documented (README, Phase 48
  audit, `docs/AI_ARCHITECTURE.md`) — real heuristic/model scoring is
  the natural first v0.4 AI Assistant Core task, explicitly out of
  scope for every v0.3 phase.
- **`execution/` remains inert.** No MT5/broker integration exists;
  GoldBot is semi-automatic by design — signals are delivered for
  manual execution, never placed automatically.
- **`data_layer/market_memory/data_cache.py` and `data_layer/live_data/session_filter.py` are unwired.**
  Built, tested-adjacent, not called by `core/pipeline.py` — no
  duplicate-fetch problem exists today for the cache to solve (the
  pipeline fetches one symbol/interval once per cycle); wire in if
  that changes.
- **Docker is foundation-only, untested end-to-end.** A `Dockerfile`
  and `docker-compose.yml` were added this phase, but this sandbox
  has no Docker daemon available to build/run them — the commands
  they invoke (`python main.py`, `python -m telegram.polling`) are
  the same already-tested commands from `docs/DEPLOYMENT.md`, so the
  application behavior inside a container is not a new code path, but
  the container packaging itself has not been built-and-run-verified.
- **`requirements.txt` remains intentionally unpinned.** A deliberate
  choice (see `docs/SECURITY.md`'s Dependency Audit) so a fresh
  install automatically receives security patches; use
  `requirements-freeze.txt` for byte-for-byte reproducibility instead.
- **Coverage is reported, not gated in CI.** `--cov-fail-under` is
  intentionally not set — see `docs/TESTING.md` for why.

## Compatibility

No breaking changes. Every existing public method signature
(`RiskManager.evaluate()`, `TradingPipeline.run()`,
`UserRepository.get_user()`, etc.) is unchanged from v0.2. Database
schema is additive-only (new indexes, no column/table renames). Every
existing Telegram command behaves identically.

## Upgrade Notes

No migration steps required from v0.2 — the database schema changes
(Phase 50's indexes) are applied automatically and idempotently on
first repository construction after upgrading, exactly like every
prior schema addition in this project's history.
