# DD-072 — Live Price Service Layer

**Type**: Director Decision Record (architecture, binding).
**Governance**: v1.1.
**Numbering note**: the Director directed that the Live Price Service be
registered as its own DD in this governance batch but did not assign a
number; recorded as **DD-072** (the next free number after the Director's
highest assignment, DD-071) to avoid colliding with any reserved number.
Flagged per No Silent Decisions.

**Context**: The Director established a clear separation between price
*collection* (Price Stream) and price *presentation* (to users), captured
in `docs/architecture/LIVE_PRICE.md`. This record formalizes the
presentation layer as an architecture decision.

## Decision

GoldBot has a dedicated **Live Price Service** layer between Memory and the
user-facing consumers:

```
Price Stream → MarketMemory → Live Price Service → {Telegram, Web Dashboard, Mobile App, REST API}
```

- **Price Stream** only *collects* prices into Memory.
- **Live Price Service** only *presents* prices: it reads through
  `MemoryReader` / snapshot / events (Memory-First — never a provider,
  never a vendor SDK) and serves each consumer.
- Adding a consumer (Telegram, Web, mobile, REST) is a **new Live Price
  Service adapter** — the Core (stream + memory) does not change.

The capability roadmap (v1.1 → v3.0) is recorded in `LIVE_PRICE.md`.

## Why

Separating collection from presentation keeps the Core stable as
consumers are added, and gives each platform a single, Memory-backed data
contract instead of bespoke provider access — the professional,
extensible shape for a multi-platform product.

## Status

**Approved — architecture layer for GoldBot presentation.** A future
implementation phase (its consumers appear later on the roadmap); the
requirement is fixed now so later work slots in without a Core rewrite.

## Applies to

All user-facing price presentation (Telegram, Web, mobile, REST/WS) and
the boundary between the Market Data Foundation and its consumers.
