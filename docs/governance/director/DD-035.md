# DD-035 — Future API Server — Memory stays internal

**Type**: Director Decision Record (Director-issued, binding).
**Governance**: v1.1. **Phase**: GoldBot v1.1 Phase 1 — Market Data Foundation.
**Context**: Platforms were shown reading MemoryReader directly.

## Decision

In the target model, external platforms talk to a **future REST /
WebSocket API server**, not to `MarketMemory` directly:

    Memory -> REST/WebSocket API -> Telegram / Mini App / Desktop / Android / iOS / Web

Memory remains an **internal layer**; the API server is a thin adapter over
MemoryReader + the event bus. This phase only guarantees the design
supports it (contracts are network-serializable); the server is a later
phase.

## Why

Keeping Memory internal and exposing a network API is what lets remote
clients (mobile, web) consume the same data without embedding the engine —
and preserves Memory-First internally.

## Status

**Approved — binding for the Market Data Foundation.** Reflected in the
architecture document (§19 (Future API Server)).

## Applies to

The GoldBot v1.1 Market Data Foundation (`data/` layer) and every future
component that reads market data through it.
